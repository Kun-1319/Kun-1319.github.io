## 一、题目信息
- **平台**: CTFHub
- **题型**: Web，SQL注入
- **考点**: 布尔盲注、length、substr、ascii、二分查找

## 二、解题思路与踩坑记录

页面提交后只返回两个词：`query_success`或`query_error`。没有数据回显，也没有报错原文。

这种页面只能回答“是”或“否”，所以思路变成：把想知道的东西变成一个真假问题，一次问一位。

`id=1 and 1=1`返回query_success，`id=1 and 1=2`返回query_error，真假通道确认。

**踩坑一：手工逐字符试太慢**

一个字符有95种可能，flag有32位，手工要试几千次。改成二分：先问“ASCII码是不是大于100”，是就往上找，否就往下找，七次定位一个字符。

**踩坑二：不知道长度**

不知道要读多少位，就没法写循环。先用`length()`把长度问出来，再按长度逐位取。

**踩坑三：空格和括号要编码**

浏览器直接输入没问题，用curl或脚本时必须urlencode，否则`>=`、空格、括号会被截断。

## 三、解题步骤

1. **确认真假通道**:

```
?id=1 and 1=1
?id=1 and 1=2
```

前者query_success，后者query_error。

2. **问长度**:

```
?id=1 and length((select database()))>3
```

真，说明库名长度大于3；再问大于4，假，得出长度4。

3. **逐位取库名**:

```
?id=1 and ascii(substr((select database()),1,1))>100
```

逐步二分，得到`sqli`。

4. **取表名**:

```
?id=1 and ascii(substr((select group_concat(table_name) from information_schema.tables where table_schema=database()),1,1))>100
```

结果`flag,news`。

5. **取字段名**:

把表达式换成columns表，限定table_name等于flag，得到`flag`。

6. **取flag**:

```
?id=1 and ascii(substr((select group_concat(flag) from flag),1,1))>100
```

按位读完，长度32，结果`ctfhub{4c55f41c0a453ceb88158b0e}`。

7. **写成脚本**:

用Python循环，每个字符做二分，判断依据是页面里有没有query_success。全程约两分钟。

## 四、总结与反思

1. 盲注的核心是把查询结果转成真假判断。页面只剩两个状态，就用这两个状态一位一位问。
2. 二分查找把每个字符的尝试次数从95次降到7次，这是效率的关键。
3. 顺序固定：先长度，后内容；先库名，后表名字段名，最后数据。
4. 手工盲注只适合演示，真实场景写脚本。脚本的核心是一个返回真假请求函数，加两个循环。

## 五、问题与解答

**问：布尔盲注和报错注入的区别。**

答：报错注入把数据塞进报错信息，一次能带出几十个字符；布尔盲注没有报错也没有回显，只能问真假，一次一个字符，慢得多。

**问：为什么要先问长度。**

答：不知道总长度，循环就没有终点。length()只用一个判断就能给出长度，成本低。

**问：二分查找为什么快。**

答：ASCII范围32到126，共95个值。顺序试平均47次，二分只要7次，因为每次都能排除一半。

**问：为什么用ascii而不是直接比较字符串。**

答：字符串比较要看排序规则，容易受大小写和字符集影响；转成数字后比较稳定，且能做加减，方便二分。

**问：写脚本算不算作弊。**

答：不算。盲注本来就必须自动化，真实渗透里也是脚本跑。关键是脚本的每个判断你都能解释。
